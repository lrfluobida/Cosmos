# 参考观察与验收契约

本契约定义补齐目录的证据格式。当前没有参考玩法测量结果；所有示例均是字段说明。机器目录见 [catalog.json](../../benchmarks/classic-pc/reference/catalog.json)。

## 状态语义

- `verified_for_edition`：外部来源事实仅适用于其记录的发行版；不算指定 EXE 的玩法证据。
- `needs_reference`：本机参考事实仍未知，不能被游戏实现代理改成通过。
- `verified_for_reference`：指定参考的规则经观察与确定性断言交叉核对，附证据；不表示生成游戏已经实现。
- `requirement_defined`：来自 spec 的目标产物验收政策，例如原创美术和浏览器性能；在后续生成产物上执行，不能用来替代参考规则。
- `provisional` / `frozen`：整个参考目录是否完成名册闭合与独立评审；冻结和最终游戏验收是两次不同判断。

## 每条事实的证据

`catalog.evidence` 的记录字段如下，证据 ID 在目录内唯一：

| 字段 | 要求 |
| --- | --- |
| `id`, `referenceId`, `entryIds` | 稳定证据 ID、本次指定 EXE 的 reference ID、覆盖的条目 ID 数组 |
| `kind` | `normal_input` 或 `deterministic_rule` |
| `status` | 收录为通过依据的记录必须为 `pass`；失败保留在原观察记录里，并将条目保持待核对 |
| `path`, `observedAt` | 可访问的本地证据/报告路径和含时区时间；评审需实际打开它们 |
| `preconditions` | 档案进度、模式、关卡、单位状态、环境和任何预置条件 |
| `steps` | 点击、按键、等待及每步定位；明确从何处开始计时 |
| `expected`, `observed` | 事先规定的观察点与实际结果，包括失败和不确定性 |

每项已核实参考规则同时引用两类证据：

1. **正常输入**：通过游戏提供的鼠标、菜单和键盘操作观察参考行为，保存截图、录像时间位置或操作记录。菜单名册的正常点击也属于此类。不能用内存改值、调试器或直接改存档替代购买、解锁和跨关链。
2. **确定性规则**：将已观察的规则转成可重复的预期值、条件表或测试向量，保留计算/断言报告。它描述参考规则与证据的推导关系，不要求此时已有生成游戏实现。

同一证据可以覆盖多项，但必须在 `entryIds` 明确列出。读取辅助状态可用于诊断；最终目标游戏的关键输入、购买、解锁和存档链仍走正常界面。后续自动验收应加入关闭输入等负例，证明测试确实检查玩家可操作路径。

## 名册、角色对应与交互闭合

- 每个植物、僵尸、关卡和子模式槽位绑定可见名称、菜单/图鉴位置、解锁前提。没有图鉴条目的变体也要单列，或附证据说明与哪一条共享规则。
- 每关记录出怪种类、数量/波次约束、随机选择条件、开始与结束条件、首次/重玩差异。五类环境、特殊关、首领与二周目分别核对，不从普通关推断。
- 商店按每件商品、档位和重复购买条件展开；花园按分区、物品、植物状态和时间事件展开；解锁以“前提 → 正常操作 → 奖励/新入口 → 存档恢复”记录。
- `catalog.interactions` 在冻结前覆盖完整植物 × 僵尸配对。每项有 `plantId`、`zombieId`、`rule`、`evidenceRefs`；无直接作用也写出可复查的结论，不能留空。共享基础规则可以复用证据，特殊状态/变体必须展开。
- `catalog.correspondence` 为后续目标游戏验收预留。每个参考单位必须有唯一原创 `targetId` 与 `referenceEntryId` 对应，必要动作和关键识别特征也要可见。冻结参考名册时不要求已经生成这些美术；生成后缺对应即不通过。
- 名册数量冲突、范围例外和偶发 bug 记录独立差异说明，标明事实、推导、未决项及处置。经典机制不能因为实现困难被归入 GOTY 或 bug 排除。

## 数值、时间和容差

`catalog.measurements` 每行对应一个具体对象的一项指标，不可用一行“植物已核对”代表全部属性：

| 字段 | 含义 |
| --- | --- |
| `id`, `entryId`, `entityId`, `metric` | 测量 ID、所属 `VALUE-*` 条目、具体关卡/角色/商品 ID、指标名 |
| `status`, `value`, `unit` | 未知写 `needs_reference` 与 `null`；已核实数值为有限数，单位明确 |
| `method` | 操作前提、计数或测时方法、画面/报告定位；记录设备与时钟来源 |
| `tolerance` | `exact` 或 `timing`；例外必须先记录理由和范围决定 |
| `evidenceRefs` | 同一 reference ID 下的观察和断言证据 |
| 补充字段 | `samples`、`measurementUncertainty`、`conditions`、`derivedFrom` 等按实际情况填；不能用推测补空 |

数值覆盖至少包括目录的六组 `VALUE-*`：每种植物的费用/生命/伤害/冷却/产出/范围/动作间隔；每种僵尸的生命/护甲/速度/啃食/技能；每关波次；全部经济值；状态持续；无尽增长。相关属性不适用时给出规则理由，不填虚假 0。

验收默认值来自 spec 第 4B 节：

- 费用、生命、伤害、购买/解锁条件等离散数值精确相等；分类规则精确一致。
- 时间采用 `abs(actual - reference) <= max(abs(reference) * 0.05, simulationStep)`。`reference`、`actual` 和 `simulationStep` 使用同一单位，运行报告记录具体模拟步长。
- 测量误差与游戏容差分别记录。先重复观察并报告样本范围，若误差大到无法判断是否在容差内，结果为待核对，不能靠放宽 ±5% 消除不确定性。
- 随机行为记录分布、允许集合、触发条件和样本方法；不把一次录像当作全部出怪规则。可固定种子的目标模拟要记录种子和回放步骤；不能声称原作具有未经验证的种子接口。
- 无尽分别覆盖循环、增长与至少 30 分钟稳定运行，报告达到的波次。有限运行不证明无限局面全部成立。

目标游戏的确定性断言复用同一生产模拟；加速测试只有在与原速模拟等价已获证明后才可用于全量规则。正常输入与原速渲染证据单独保留。最终用户试玩仍负责手感、辨识度和整体体验。

## 冻结交接

冻结前由独立评审实际检查：指定程序运行证据、名册闭合、所有参考条目的双类证据、全部具体数值、交互配对、发行版差异及范围处置。评审不得只读取校验器输出。

所有未决项解决后更新 `reference.blockers`、`catalog.closure` 和 `reference.freezeReview`，冻结评审至少包含 `status: approved`、`reviewer`、`evidencePath`。评审者身份与实现者独立。`--require-frozen` 应在完整生成关口执行；不能以普通校验退出码 0 代替它。

本批校验器是保守的结构检查，不会读取或运行证据文件，也不能验证其真实性。它会拒绝仍有未知条目的冻结声明，但不能自行证明每种属性已穷尽。COS-14 应在此格式上实现完整产物验收，不能把本批脚本当作游戏通过证明。
