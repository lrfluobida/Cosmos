## 用户可观察行为

1. 新普通运行以 structured-design-plan/3 冻结任务工具和规则，合法修订继承选择。保持 /2 的有效草稿写前保护。旧运行按原冻结选择读取和恢复。
2. 作者如果把已确认的体验 criterionId 填入 assert 或 wait-for 的 acceptanceId，反馈给出实际阶段、零基下标、步骤 id、误填值及其来源，并列出有界的原始玩法验收 ID。这同样适用于 debug 观测。体验条目由设计的 experienceMapping 对应，最终由真人试玩。普通未知字符串保持准确诊断。对不可信值做 JSON 引用与长度限制，复用原写入反馈上限。
3. /3 的 write-game-plan 增加 repair-acceptance-ids。一次只能操作 main 或 reopen 其中之一，作者明确给 1 至 16 条 corrections，每条只有 stepId、from、to。目标在选定阶段中按 id 唯一且为 assert/wait-for，原 acceptanceId 是与 from 相同的字符串并且不在原玩法清单内，to 在该清单内。重复目标、陈旧值、缺失阶段、非法或多余字段均拒绝。整批验证后经原有授权和写前检查一次写入；任一失败则保留原字节。成功只改变所列 acceptanceId，保留步骤顺序、观测、期望、其他步骤、设计和要求引用。
4. 所有 ID 均从本次冻结需求取得。工具不推断映射，不把体验升级为客观通过，不替作者修改测试标准。编辑后继续运行原结构检查，并交给原独立审查和浏览器验收流程。
