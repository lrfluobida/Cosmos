## Problem and verified boundary

Cosmos must let its independent reviewer make its own supported judgment within an existing bounded session. This is a platform scheduling change; it does not repair the generated game or grant a new validation window.

R75 evidence is retained under `.cosmos/public-validation/room-20261116-review-followup-75/run` and `.cosmos/planning/r75-independent-observation/final-review.json`. The native review journal contains sixteen settled assistant replies, all `toolUse`, then a local seventeenth assistant error, `Session request limit reached`. Paid author/reviewer totals are 5/16 requests and 31,693/458,173 micro-CNY (489,866 total). Native build, 398 browser steps and 31 media checks passed, source was unchanged, and eight screenshots were supplied. These facts do not constitute an independent verdict.

R75 read the complete save203/resume201/media34/series406 navigation indexes. The six-key detail request returned only lines 1–1419 of 5291 and was not continued. The final paid request read the media manifest and media specification. The independent observer found the returned navigation exactly matches production; this is not another COS-231 defect. R75 remains failed/incomplete, review pending, automatic acceptance not passed, user experience not confirmed, and permanently closed. No R76 authorization follows from this design.

Current `src/providers/pi.ts` increments `requests` before dispatch and refuses when `++requests > maxRequests`. The ordinary entrypoint sets `maxRequests:16`. Neither `src/roles/factory.ts`'s reviewer prompt nor the native loop reserves a decision request. The author build reserve already demonstrates the installed SDK seam: `session.agent.finishTurn`, `setActiveToolsByName([])`, a custom message, and a native continuation with unchanged request accounting. Native SDK 0.99.2 refreshes selected tools before the next turn. Active tools alone are not enough: codemode/deferred tools remain callable and must be rejected.

`requestReview` in `src/runtime/repair/protocol.ts` sends a malformed-output correction through `reviewer.prompt`, not `readonlyPrompt`. Only the existing design reasoning-exhaustion recovery uses `reviewVerdictCorrection`. Therefore a prompt-only reminder or only disabling tools in `readonlyPrompt` does not establish the boundary needed here.

## Options and decision

1. Add only the sixteen-request limit and prioritization instructions to the reviewer prompt. This is the smallest change and is useful guidance, but a model can still issue sixteen tool replies. A scripted reproduction retaining those sixteen replies must still fail on current source; changed instructions cannot enforce a different next turn.
2. **Selected: retain sixteen total requests, reserve request 15 for a native tool-free decision and request 16 for the existing single protocol correction.** At the end of tool response 14, the trusted host disables all callable tools and asks for the current independent result. Early completed responses still return immediately. A later externally prompted correction uses the same live session, no tools, and one request. This reuses the existing SDK boundary, parser and correction record rather than creating another retry authority.
3. Reserve only request 16 for the first decision. This permits one more read round but leaves no request for malformed JSON correction. Raising the request limit, output floor, budget or deadline is excluded; none is supported by R75's failure mechanism.

The selected policy trades the last two possible tool rounds for a decision and possible correction. It cannot guarantee that fourteen rounds suffice to inspect every requirement. A truthful incomplete outcome is explicitly acceptable. The source gate proves an available bounded decision opportunity, not a guaranteed successful verdict or the correctness of the R75 game.

## State machine and request arithmetic

The helper tracks one monotonic phase: reading → final → returned → correction → done; terminal failure is irreversible. It also records that the initial external prompt and any correction have been claimed before awaiting work. A valid early model `stop` may move directly from reading to returned. Parsing stays outside this state machine.

| Situation | Host action | Next request / outcome |
| --- | --- | --- |
| Initial prompt, tool reply 1–13 | Keep current tools and native tool results; do not add per-round prompts. | Ordinary continuation, original guards. |
| Tool reply 14 completes | Finish its actual tools, check cancellation, reject codemode/deferred registries, set active tools to `[]`, verify active and callable sets are both empty, append one host closing message. | Continue natively to request 15, preserving full history and images. |
| Early completed `stop` with no tool calls/results | End current native turn immediately; do not force fourteen reads or add a final request. Mark initial response returned. | Existing parser accepts or requests its existing one correction. |
| Final request 15 completes with `stop`, including empty text or partial/invalid JSON | End native loop and return the actual text without semantic editing. | Valid proposal returns; otherwise `requestReview` may claim its existing correction slot. |
| First external correction after any returned initial response | Claim local correction before awaiting; irreversibly disable/check tools even after an early malformed response; call the existing single-request read-only path in the same native session. | At most one next request; normally request 16 after reserved final 15. Keep the original thinking policy. |
| Correction returns valid `stop` | End, return actual text to the unchanged parser. | Existing exact input/evidence checks decide. |
| Correction returns malformed/empty JSON or stale versions | Return text, no more local prompt may dispatch. | Existing `ReviewProtocolError`; no second correction or request 17. |
| Final or correction attempts `toolUse` | No registered tool may execute. Reject as `incomplete` and return native `end`, even if SDK normally continues after an unknown tool result. | No auto-followup, no correction opportunity after this terminal native failure. |
| Request 15/16 has `length` (reasoning only, visible partial JSON, or partial tool call) | Keep current coding truncation failure. Do not broaden design-only `pendingReview`. Account actual usage before failure; no partial tool executes. | `incomplete`; no correction for terminal coding length, no additional request. |
| Model cannot independently judge from inspected evidence | Model states review is incomplete and identifies unassessed material. Do not manufacture `approved` or a defect. The statement remains an invalid proposal under the current schema. | Existing optional single correction may restate inability; ultimately `ReviewProtocolError` / insufficient-evidence failure with review pending. |
| Third external prompt, second read-only call, concurrent correction or a different error object | Reject without provider dispatch. A direct `readonlyPrompt` consumes the same local claim as `.prompt`, never another allowance. | No additional model call. |
| Abort, close, stale authority, deadline/budget rejection, unknown usage, provider/model error | Existing Pi/controller failure remains authoritative and irreversible. | No reserved-turn bypass; no new request authority. |

For the longest successful trajectory, `14 tool responses + 1 completed final + 1 correction = 16`. If final 15 is valid, only fifteen requests are sent. An early response and its correction consume only their actual request count; the unused reserved capacity is not an invitation to resume reading. The read-only path's per-call single request and the selected session's once-only local correction claim both apply. The correction record remains the existing `review-correction.json`, written durably by `requestReview` before dispatch. Native prompt claims do not substitute for that durable record; they prevent direct/multiple APIs from reopening this session's phase.

In particular, if response 14 is a natural `stop` with malformed JSON rather than a tool reply, return it immediately. The outer protocol correction is then request 15 with tools disabled, consumes the only correction, and cannot be followed by request 16. Test this boundary explicitly as well as an earlier malformed response; reaching the threshold never bypasses the external-prompt correction rule.

Both final and correction preserve the original coding thinking level (`low` unless already configured otherwise), 8192 output maximum, unchanged 4096 affordability floor, timeout and serialized image quote. Use the existing read-only path without the design verdict mode that turns thinking off. Add strict terminal checks through the selected helper instead. No extra monetary reserve, forced lower floor, automatic summary or history compaction is introduced.

## Prompt and evidence semantics

The initial selected reviewer guidance states that the session permits at most sixteen model response rounds, fourteen may use tools, the host reserves a decision and one possible format correction, and a supported early verdict should be returned promptly. Prioritize required inputs and decisive evidence; follow continuation offsets whenever a chosen detail is partial. Do not claim all selected details were read if pagination remains.

The one closing message says: all tools are now disabled; give your own independent result using only facts already inspected and the existing exact review schema; preserve genuine defects and exact input/evidence identities; if evidence is insufficient to reach either supported verdict, explicitly state incomplete and name what was not assessed. The host will keep the task incomplete. A tool-free turn cannot invent missing observations.

Append the same honesty rule to the selected correction prompt: correcting format does not authorize inventing facts, calling missing reads successful, or changing an incomplete statement into approval. Keep the generic or specialized coding schema already supplied by `requestReview` intact. No new accepted verdict enum, incomplete JSON schema, synthesized finding or approval fallback is added.

The existing ordinary coding concern protocol already allows an unresolved concern and supported `changes_requested` when current evidence does not establish its claimed behavior. Preserve this route: name the actual concern, unmet requirement and precise missing/unassessed evidence; do not pretend to have observed a source defect. Where that existing schema supports such a judgment, the reviewer may return it. Where the reviewer cannot support either existing verdict, retain the explicit incomplete failure above. Tests must cover both the generic parser and the actual `parseCodingConcernReview` path; insufficient inspection is never converted into resolved host evidence.

Retain every original user/assistant/tool message and all eight image blocks, raw reads, exact navigation/detail results, candidate binding, frozen input versions and evidence IDs. Add only the bounded host message and current correction prompt. The hook never fetches evidence, patches a response, decides whether a defect exists or changes the parser. Original native journals and historical ledgers remain untouched.
