# COS181 · 保留成功写入钩子后的有界预算收尾

## 问题与范围

基线：`11a710a06d06dc9339620591faabfcfb4b255dd7`。

R33 暴露 COS180 回归：成功写入的 `turn_end` 钩子在判断事件资格之前调用 `requireCompactionActive`。普通请求因本地最低输出预留不足而未发送时，`throwIfFailed` 抛出可收尾的 `pendingFinalization.error`，随后钩子的 `admissionFailure` 将它变成持久失败，使 `budgetFinalization` 返回空。

R33 的普通请求输入为 84066B、最低输出为 8192，报价 233668 微元超过作者可用 230338 微元；原有 4096 上限只读收尾仍可能容纳。原记录没有 `author-correction-started`。映射和验收计划仍缺失；恢复收尾资格不产生这些文件，也不代表游戏完成。

本任务只调整 `src/providers/pi.ts` 的检查顺序：

- 无条件清除 `pendingCheckpoint` 并通过 `takeWrites` 消耗本轮可信写入身份。
- 先检查只读、禁用压缩、结算记录及完整成功写入事件等纯资格条件；不符合的事件直接结束钩子。
- 只有符合资格的事件才检查压缩活动状态、原有权限和后续原生关联。
- 真实权限或关联失败继续锁定失败；取消、截止时间和未知费用继续受原有保护。不得全面忽略预算错误。

原请求计数、输出上限、模型、分配额、评审预留、截止时间和权限保持。未发送的普通请求不收费，也不退还计数槽。只读收尾仍与格式纠正共享唯一机会，最多一次、4096 输出上限、无可调用工具。

## 验证

使用真实角色工厂、受限文件工具、Pi 原生会话和 TEMP 账务，仅模型传输为合成夹具。覆盖两个实际钩子路径：

1. 原生可选摘要跳过，后续普通请求在本地输出下限处被拒绝。
2. 成功写入检查点和原生摘要完成，后续普通请求在相同边界被拒绝。

两者均核对原生错误来源、未发送请求无新增账务、原请求计数与 64 上限、一次无工具只读回复、原分配与截止时间、原文件和完整原生日志前缀。只读回复明确保留缺失的 `acceptance-plan.json`，独立验收仍待执行；拒绝第二次收尾。

原检查顺序下两条回归均在来源为空处失败（RED 0/2）；最小补丁后两条通过。受影响的成功写入、只读、真实权限失败和真实取消代表与新回归合计 6/6、0 skip；最终缺失文件回复断言调整后仅重跑新回归，2/2、0 skip。`npm run typecheck` 与 `npm run build` 均退出 0；未改动的请求计数及原生关联保护复用已有证据，不重复扩大测试。
